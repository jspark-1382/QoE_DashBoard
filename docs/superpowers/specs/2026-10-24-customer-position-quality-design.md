# 고객 위치 추정 품질 검토와 개선 설계

검토일: 2026-10-24 · 코드: `8b7dfbf` · 데이터: MDT 2026-09-15, revision `9a822f8105670b24606e`

상태: 코드·로컬 데이터 검토 완료, 개선안 제안. 이 문서의 개선 알고리즘은 아직 제품에 적용하지 않았다.

## 1. 결론과 목적

현재 추정기는 문제 지역을 조사하는 참고 위치로 사용할 수 있지만, 정확한 고객 위치나 60m 단위 문제 지점을 입증하는 모델로 보기 어렵다. 통화 분리, 원본 좌표 보존, 단일 기지국의 고객 좌표 대체 억제는 유지한다. 우선 재현 가능한 오류와 근거 손실을 고치고, GNSS 기준의 누출 없는 평가에서 단순 기준선보다 좋아지는 방법을 선택한다.

사용자는 분석가이며 원본 계약번호와 MDT 고객 좌표를 대조하려 한다. 좌표계는 사용자가 확인한 UTMK / EPSG:5179다. 건물·호실 수준의 위치나 실시간 길 안내는 목표로 가정하지 않는다. 달성 거리 목표는 검증 결과를 보고 정하며, 현재 자료만으로 50m/100m 정확도를 약속하지 않는다.

## 2. 현재 경로와 지켜지는 원칙

`scripts/mdt_pipeline.py` → EPSG:5179 변환(`mdt_gnss.py`) → 고객·일자 파티션 → `lib/analyst/data.ts`의 통화별 정규화 → GNSS 없는 행에 `estimateAdaptive()` → 지도 및 사전 생성 현황.

- GNSS 관측을 무선 추정으로 덮어쓰지 않는다. 원본 UTMK를 보존한다.
- 추정 시간창은 통화 안에서 구성하며, 같은 사이트의 여러 셀을 독립 기지국으로 중복 계산하지 않는다.
- 분석가 화면은 단일 사이트의 좌표를 고객 추정점으로 사용하지 않는다.
- 현재 모델은 최대 ±60초의 serving site 관측을 합친다. 이웃 셀을 동시에 관측한 다변측량과는 근거가 다르다.
- 기지국 좌표 매칭과 고객 위치 정확도는 다른 성질이다. 매칭률이 높아도 위치 오차가 작음을 뜻하지 않는다.

## 3. 이번 실제 데이터 감사

원본을 수정하지 않고 10,250개 파티션·25,548개 통화를 검사했다. 통화 내 이벤트는 541,707개, RSRP 있는 이벤트는 345,901개, GNSS는 44,433개이며 GNSS 보유 통화는 3,592개다. 전체 이벤트 596,865개와의 차이는 통화 밖 이벤트다.

추가로 원본 XLSX 598,926행을 스트리밍 검사했다. `(base_date,svc_cont_id,lte_vc_div)` 25,548개 키는 모두 비어 있지 않은 IMS가 정확히 1종류이며, 시작·종료시간·통화구간 충돌은 각각 0건이다. 현재 급점프를 서로 다른 IMS 통화의 합침으로 설명할 근거는 없다. IMS 하나가 단말 하나임을 보장하거나 GNSS의 시각 의미를 입증한 결과는 아니다. 원본 숫자 좌표에는 0/0 자리 채움 값이 포함돼 숫자 존재만으로 GNSS 유효 수를 세지 않았다.

### 3.1 거리 모델과 기준 좌표

- 현재 `n=0.75`, 기준 RSRP `-83.7dBm@100m`, 거리 제한 `20–1500m`다. 보정 주석은 10/14의 이전 마스터 맞춤 affine 자료를 가리키며 현재 EPSG:5179 학습·검증 산출물은 없다 (`adaptive-config.ts:4–8,20–21`). 이 계수의 오류를 단정하는 것이 아니라 현행 입력에 대한 유효성 근거가 부족하다는 판단이다.
- RSRP 345,901개 중 63,329개(18.3%)는 20m, 118,941개(34.4%)는 1500m로 포화한다. 합계 52.7%에서는 RSRP 차이가 거리 차이로 반영되지 않는다.
- GNSS와 기지국을 연결한 43,385쌍의 실제 좌표 간 거리는 중앙 191m, P90 680m다. RSRP와 log10 거리의 상관계수는 -0.255로 약하다. 지역·주파수·안테나·실내외를 통합한 단일 거리식의 적합성을 검증해야 한다.
- 양의 시간차를 가진 같은 통화 내 인접 GNSS 29,525쌍 중 3,136쌍(10.6%)이 현재 상한 200km/h를 넘는다. 이를 모두 GNSS 오류라고 확정하지 않는다. 원본 통화 묶음·단말 구분·타임스탬프 품질도 함께 확인해야 한다.

### 3.2 좌표를 숨긴 탐색 평가

GNSS 보유 통화 중 `SHA256(location-audit-v1:고객ID:통화ID)`가 작은 300개를 고정 선택했다. 각 통화의 GNSS 좌표를 **모두 숨긴 후** 현행 `normalizeDay()`로 재계산했다. 모델 계수는 재학습하지 않았다. 3,612개 기준 지점 중 2,625개(72.7%)에 추정점이 생겼다. 아래 비교는 현행 추정과 매칭 기지국 기준점이 모두 존재하는 **같은 2,609개 지점**이다.

| 방식 | 중앙 오차 P50 | P90 | P95 |
|---|---:|---:|---:|
| 현재 무선 추정 | 269m | 1,321m | 1,534m |
| serving 기지국 위치 기준선 | 233m | 930m | 1,578m |

현재 추정이 더 가까운 지점은 1,328/2,609(50.9%)다. 중앙값과 P90에서는 우월하지 않았고 P95에서는 조금 작았다. 이 기준선은 오프라인 비교용이며 기지국 좌표를 제품의 고객 위치로 다시 제공하자는 제안이 아니다.

인접 GNSS가 120초 이내이고 이동속도 200km/h 이하인 간단한 일관성 부분집합에서도 같은 지점 2,192개 기준 P50은 264m 대 232m, P90은 1,292m 대 934m였다. 이 필터는 정답 좌표의 정확도를 보장하지 않는다.

추정된 전체 2,625개 지점 중 GNSS에서 60m 이내는 200개(7.6%), 100m 이내는 439개(16.7%)였다. 모델 반경 중앙값은 약 1,281m이고 해당 반경의 GNSS 포함률은 2,326/2,625(88.6%)다. 반경은 현재 확률로 보정되지 않았으므로 90% 신뢰구간이라고 부를 수 없다.

**해석 한계:** 하루·한 자료의 탐색 재생, 이벤트 가중 통계다. 같은 고객의 반복 관측을 독립 표본으로 볼 수 없고, 과거 보정에 이 자료가 포함됐을 가능성을 배제하지 못했다. GNSS 자체의 정확도·수집 상태가 검증되지 않아 현장 정확도 인증이나 독립 테스트셋 성적으로 사용하지 않는다. 향후 고객별/통화별 집계와 고객 단위 불확실성 구간도 보고한다.

로컬 재현: `node outputs/location-audit/2026-10-24/audit.cjs`. 진단 도구와 입력은 Git 제외 경로에 보관하며 원본 계약번호·좌표·IMS 값은 이 문서에 넣지 않는다. 식별자·좌표 없는 집계 스냅샷은 [추정 비교 결과](../reviews/2026-10-24-location-audit-summary.json), [원본 묶음 검사](../reviews/2026-10-24-location-source-grain.json)에 보관한다. 합성 오류는 `node outputs/location-audit/2026-10-24/reproduce-model-issues.cjs`로 재현했다.

## 5. 권장 설계

### 5.1 데이터와 품질 계약

원본 좌표와 원본 라디오는 그대로 보존한다. 별도 파생 필드로 `positionQuality=plausible/suspect/rejected/unknown`, 이유, 사용 정책을 둔다. plausible은 시계열상 모순을 발견하지 않았다는 의미이며 검증된 절대 정확도를 뜻하지 않는다. 의심 관측은 분석가가 볼 수 있지만 기본 앵커·정밀 집계에서는 제외한다. 원본 시계열에서 동일 시각 충돌·급격한 이동·오래 반복되는 좌표·순서 오류를 검사한다. 반복 좌표만으로 실내나 오류를 단정하지 않는다.

엔진은 `source`, `method`, `usedSites`, `windowSec`, `anchorDeltaSec`, `residualM`, `geometry`, `jump`, `warnings`, `uncertaintyKind`, `radiusM`를 반환한다. GNSS 정확도가 없으면 null로 보존하며, 모델상의 앵커 허용거리는 관측 정확도와 다른 설정으로 정의한다. 결과의 최종 좌표를 확정한 뒤 속도·잔차·배치·판정을 계산한다.

1차 정책의 구체값은 제안자가 다음과 같이 고정한다. 같은 통화의 시간순 관측에 대해 유효 범위 밖 좌표는 rejected, 필수 시각/CRS/출처가 없으면 unknown으로 둔다. 양의 시간차 120초 이내 인접 GNSS가 200km/h를 초과하면 양끝을 모두 suspect로 두고, 같은 시각 좌표가 1m보다 다르면 해당 시각의 충돌 점을 모두 suspect로 둔다. 어느 점이 정답인지 임의로 선택하지 않는다. 한 번의 검사에서 위반 쌍을 모두 표시하며 suspect를 다음 점으로 재귀 전파하거나 나중에 임의 승격하지 않는다. 위반 쌍에 참여하지 않은 후속 정상 관측은 plausible이 될 수 있다. 긴 공백은 좌표 오류로 단정하지 않고 연결과 앵커 사용만 끊는다.

정확도 정보 미제공만으로 GNSS를 rejected로 두지 않는다. plausibility를 통과한 GNSS의 절대 정확도는 계속 unknown이다. unknown/suspect/rejected는 기본 앵커·정밀 집계에서 제외하고 원본 검토 레이어에 보존한다. 기존 실측은 GNSS 품질 정책을 소급해 조용히 제거하지 않으며, 별도 출처의 기존 현황을 유지하고 품질 미검증을 표시한다. 이 실측을 GNSS 기준 정답·앵커·성능 평가로 재사용하지 않는다.

### 5.2 방법 선택과 보류

1. 시각·품질이 확인된 GNSS를 관측 위치로 제공한다.
2. 같은 통화의 품질 확인된 양끝 GNSS가 있고 10초 이내의 짧은 공백이면 시간 보간을 후보로 비교한다. 속도·양끝 일관성·중간 핸드오버의 모순을 검사하고 출처는 보간으로 표시한다. 10초는 최초 비교 설정이며 검증 전 기본 제품 정책으로 확정하지 않는다. 미래를 사용하는 보간은 오프라인 재생에만 적용한다.
3. 라디오만 있는 구간에서는 현행 모델, 사이트 가중 중심, median 대표값+robust 손실, 다중 초기값을 같은 평가 자료로 비교한다. 정확도가 확보되지 않은 거리식의 복잡성보다 기준선 대비 개선과 보류 정책을 우선한다.
4. 1사이트·불량 기하·과한 시간창·미해결 매칭·미검증 앵커는 정밀 대표점을 보류하거나 넓은 참고 영역으로 제공한다. 2사이트는 해를 유일하게 식별한 것으로 표시하지 않는다.

### 5.3 검증과 채택 기준

- 라디오 단독: 통화의 모든 GNSS를 숨긴다. 같은 통화의 다른 행에서 정답이 새어 들어가면 실패다.
- GNSS 보조: 5/10/30/60/120초 연속 공백을 만들고 숨긴 구간의 좌표를 앵커·보정 학습에서 제거한다. 양끝/한쪽 앵커를 따로 평가한다.
- 예측기에 전달하는 GNSS 품질·앵커 적격성은 마스킹 **이후에 남은 관측만으로 다시 계산**한다. 숨긴 정답의 품질 검사는 평가 대상 선정에만 사용하며, 품질 플래그·경고·정답 기반 거리까지 예측 입력에서 제거한다. 평가 대상 선정 규칙은 모델 결과를 보기 전에 고정한다.
- 고객을 보정/검증/잠금 테스트로 분리해 통화 중복을 차단한다. 공간 분리는 아래의 별도 스트레스 평가에서 수행한다. 한 날짜 자료로 날짜 외 일반화를 주장하지 않는다.
- 주 평가는 고객 ID의 고정 hash로 fit/validation/radius-calibration/locked-test를 60/20/10/10%로 나눠 같은 지역의 새 고객에 대한 평가로 한정한다. 공간 밖 검증은 별도 스트레스 평가다. EPSG:5179의 1km 격자와 200m 완충 구역을 사용하고 고객↔격자 연결 그룹을 분리한다. 거대 연결 그룹 때문에 유효 분할이 안 되면 공간 밖 평가는 불충분으로 보고하고 고객 평가를 공간 일반화로 이름만 바꾸지 않는다. 공간 분할 규칙도 모델 결과를 보기 전에 고정한다.
- 동일 공통 표본의 P50/P90/P95, 60/100/300m 이내 비율, 위치 반환 비율, 보류 비율을 함께 기록한다. 모델마다 추정 가능한 표본이 달라지는 선택 효과도 별도로 보고한다. 이벤트 가중과 고객/통화 가중 결과를 구분한다.
- 제안 채택 기준: 고객 단위 신뢰구간과 함께 P90이 기준선보다 10% 이상 개선되고 P50·커버리지의 중대한 후퇴가 없을 때 후보를 채택한다. 최초 기준은 P50 5% 이내·커버리지 5%p 이내 후퇴로 둔다. 이는 제안자의 출발 기준이며 검증 전에 고정한다. 달성 후보가 없으면 더 단순한 참고 영역/보류 방식을 유지한다.
- 보정 반경은 별도 calibration 분할에서 경험적 포함률을 맞추고 잠금 테스트에서 확인한다. 데이터가 적은 구간에는 보정된 신뢰 수준을 부여하지 않는다. 신뢰점수 /100을 정답 확률로 표시하지 않는다.
- 첫 보정 목표는 **품질 기준을 통과한 제공 GNSS 좌표에 대한 90% 포함률**이며 실제 고객 위치의 절대 정확도 보장이 아니다. 방법/품질별 보정 구간은 최소 50명의 독립 고객과 200개 기준 지점을 요구하고, 부족하면 공통 보정 또는 heuristic/unknown을 유지한다. 고객 단위 bootstrap으로 포함률 구간을 함께 보고한다. 모델·보류·품질 정책·반경을 모두 고정한 뒤 마지막 잠금 테스트를 한 번 수행한다.

### 5.4 현황 집계와 모델 버전

GNSS/보간/무선 추정의 근거와 품질을 격자별로 보존한다. 기본 현황은 적격 관측 위치를 사용하고, 불확실한 추정 영역은 별도 조사 범위로 조회한다. 원본 통화 수·평가 분모는 위치 보류로 줄이지 않는다. 60m는 표시 격자일 뿐 정확도 약속이 아니다. 추정점의 미검증 반경을 정규분포로 가정해 인접 셀에 확률 배분하지 않는다. 필요 시 검증된 범위로 더 큰 공간 단위를 제공한다.

`sourceRevision + normalizationVersion + estimatorVersion + configHash + qualityPolicyVersion`을 현황 산출물과 상세 캐시의 동일 키로 사용한다. 불일치하면 명확한 갱신 상태를 제공하고 새 현황을 원자적으로 발행한다.

### 5.5 이후 확장 후보

통화 내 198,821개 이벤트에 이웃 측정 배열이 있다. 원본은 `n1_pci/n1_rsrp/n2_pci/n2_rsrp`만 있고 이웃 Cell ID·주파수는 없다. PCI·확인된 주파수·지역으로 셀을 유일하게 매칭할 수 있는 추가 마스터/관측을 확보하면 동시 이웃셀의 RSRP를 사용한다. serving 주파수를 이웃 주파수로 가정하거나 PCI만으로 전역 유일 기지국을 정하지 않는다. 이 정보를 쓴 fingerprint/kNN과 경량 회귀는 추가 후보이며, 한 지역·하루의 자료에 과적합하지 않도록 공간·날짜 밖 검증 이후 채택한다. 안테나 방위각·높이·기준신호 전력·TA 등이 있으면 추가 실험하되 현재 필드가 있는 것으로 가정하지 않는다.

## 6. 선택과 구현 순서

추천은 **현재 엔진을 유지하며 검증·품질·판정 일관성을 먼저 보강한 뒤, GNSS 보조와 무선 추정을 비교 가능한 방식으로 개선**하는 것이다. 엔진 전면 교체나 대형 ML 모델 도입은 후순위다.

1차: 기준 데이터/누출 없는 평가 → 확정 오류 수정 → GNSS 품질과 결과 근거 보존 → 현황 적격성·모델 버전.

2차: 짧은 공백 GNSS 보간, robust 무선 모델·단순 기준선 비교 → 반경·신뢰도 보정.

3차: 셀 마스터 보강 후 이웃 측정·fingerprint 비교, 다른 날짜·지역 검증.

구현 계획: [작업 단위와 합격 조건](../plans/2026-10-24-customer-position-quality.md). 독립 코드 검토 2건과 계획 구현 가능성 검토를 반영했다. 기존 위치 회귀 15개 검사군은 그대로 통과했으며, 새 합성 사례는 현재 검사만으로 발견되지 않는 오류를 확인했다.

## 7. 외부 근거

채널 모델은 환경·주파수·가시선 조건과 shadow fading을 구분한다. 이를 현재 계수로 바꾸라는 뜻은 아니며, RSRP 하나를 정밀 거리로 해석하지 않아야 한다는 배경이다. [ETSI / 3GPP TR 38.901, 7.4.1](https://www.etsi.org/deliver/etsi_tr/138900_138999/138901/18.00.00_60/tr_138901v180000p.pdf).

같은 집단의 상관된 관측을 행 단위로 나누거나 평가 정답을 전처리·학습에 노출하면 성능이 낙관적으로 보일 수 있다. 고객/공간 분리와 숨긴 GNSS 차단은 이 원칙을 본 데이터에 적용한 설계다. [scikit-learn 교차 검증](https://scikit-learn.org/stable/modules/cross_validation.html), [데이터 누출 방지](https://scikit-learn.org/stable/common_pitfalls.html#data-leakage).
